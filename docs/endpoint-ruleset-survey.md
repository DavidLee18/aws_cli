## 4. Rule shape

- **Rule counts per service** (counting every rule node, trees included):
  min 2, Q1 20, median 20, Q3 26, max **389** (`s3`). Next largest: `kinesis` 167,
  `s3-control` 141, `dynamodb` 77, `ecr` 54, `iam` 54 — the tail is very short.
- **Max tree nesting depth**: **18** (`s3`). Distribution of per-service max depth:

  | depth | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 | 13 | 15 | 16 | 18 |
  |---|--:|--:|--:|--:|--:|--:|--:|--:|--:|--:|--:|--:|
  | services | 3 | 1 | 1 | 38 | 262 | 40 | 81 | 1 | 1 | 1 | 1 | 1 |

  A recursive evaluator is fine; depth ≤ 18 needs no trampolining.
- **Rule object keys**: `type` (9875), `conditions` (9875 — always present, often
  `[]`), `rules` (4486 tree), `endpoint` (2786), `error` (2603),
  `documentation` (21, on both `tree` and `endpoint` rules, e.g. `acm`'s
  `"Use custom endpoint if provided"`). `conditions` is present on every rule.
- **`error` is always a string** (0 non-string cases); it may contain template
  interpolations, e.g.
  `` Client was configured for partition `{partitionResult#name}` but Kvs ARN has `{parsedArn#partition}` ``.

### `endpoint` object keys

Only three, and effectively always all three: `url` 2786, `properties` 2769,
`headers` 2767.

**Surprise:** `url` is *not* always a string. 427 sites have
`"url": {"ref": "Endpoint"}` (the custom-endpoint passthrough rule); 2359 sites
have a template string. The value grammar for `url` is the full value grammar
(ref / template / fn), so do not type it as `String`.

### `properties` contents (3 distinct keys)

| key | sites | value |
|---|---:|---|
| `authSchemes` | 446 | array of scheme objects |
| `backend` | 97 | always the string `"S3Express"` (`s3`) |
| `metricValues` | 12 | always `["O"]` (`dynamodb`, account-ID endpoint metric) |

`authSchemes` element keys: `name` (468), `signingRegion` (430),
`signingName` (300), `signingRegionSet` (35), `disableDoubleEncoding` (227).
`name` values: `sigv4` (389), `sigv4-s3express` (44), `sigv4a` (35).

**Signing region vs endpoint region.** `signingRegion` is frequently *not* the
endpoint's region: 16 distinct values, including the template `{Region}` (187),
hard-coded `us-east-1` (67), `{PartitionResult#implicitGlobalRegion}` (64),
`us-gov-west-1` (22), `{bucketArn#region}` (15, S3 ARN-region overriding),
plus `us-iso-east-1`, `us-isob-east-1`, `us-isof-south-1`, `eu-isoe-west-1`,
`eusc-de-east-1`, `cn-north-1`, `cn-northwest-1`. In the test corpus, **278
success cases have a `signingRegion` that does not appear in the URL at all**
(e.g. `iam` → url `https://iam.amazonaws.com`, signingRegion `us-east-1`).
The interpreter must return the resolved auth scheme alongside the URL; the
signer cannot re-derive the region from the host.

`sigv4a` carries `signingRegionSet` (an array, typically `["*"]`) instead of
`signingRegion`, plus `disableDoubleEncoding: true`.

### `headers`

Only two header names exist in the whole corpus, both `s3-control`, both with
array-of-template values:
`x-amz-account-id: ["{accessPointArn#accountId}"]` (10 sites) and
`x-amz-outpost-id: ["{outpostId}"]` (10 sites). Values are `list<template string>`.

## 5. Template strings

Two forms only, across every template-bearing position (url, error, header
values, `properties` strings):

| Form | Occurrences | Example |
|---|---:|---|
| plain `{Name}` | 4885 | `https://s3.{Region}.amazonaws.com` |
| attribute `{Name#attr}` | 4576 | `https://access-analyzer-fips.{Region}.{PartitionResult#dualStackDnsSuffix}` |

- **No indexing syntax (`{Foo[0]}`) appears in any template** — indexing exists
  only inside `getAttr` path strings (`resourceId[0]`). 
- **No multi-segment paths** (`{A#b.c}`) appear either — attribute access is
  exactly one level deep.
- **No brace escaping anywhere**: zero occurrences of `{{` or `}}` in the corpus.
  A minimal implementation can treat `{` as always starting an interpolation,
  but supporting the spec's `{{`/`}}` escapes costs nothing and is safer.
- Distinct plain refs used in URLs (14): `Region` (2010), `Bucket` (117),
  `s3expressAvailabilityZoneId` (80), `uri_encoded_bucket` (25),
  `OperationType` (24), `StreamIdPrefixValue`/`StreamIdSuffixValue` (12 each),
  `accessPointName` (11), `AccountId` (9), `EndpointId` (6), `Endpoint` (5),
  `HttpsCustomEndpointSuffixValue`, `PlainCustomEndpointSuffixValue`, `outpostId` (4 each).
- Interpolated bases include *assigned variables*, not just parameters:
  `PartitionResult` (3799), `partitionResult` (332), `url` (238), `bucketArn` (78),
  `arn` (33), `accessPointArn` (23), `arnPartition` (19), `bucketPartition` (17),
  `ParsedArn` (16), `parsedArn` (13), `regionPartition` (4), `mrapPartition` (3),
  `resourceArn` (1). So template resolution reads the same scope as `ref`.
- Complete set of `{X#attr}` pairs observed (34), by attribute:
  partition-ish (`dnsSuffix`, `dualStackDnsSuffix`, `implicitGlobalRegion`, `name`),
  ARN-ish (`partition`, `service`, `region`, `accountId`),
  URL-ish (`scheme`, `authority`, `path`, `normalizedPath`).

## 6. `smithy.rules#endpointTests` format

Top-level object keys, present on all 431: `version`, `testCases`.
`version` is `"1.0"` (429 models) or `"1"` (2 models) — **parse it loosely.**

```jsonc
{
  "version": "1.0",
  "testCases": [
    {
      "documentation": "For region us-east-1 with FIPS enabled and DualStack enabled",
      "params":   { "Region": "us-east-1", "UseFIPS": true, "UseDualStack": true },
      "expect":   { /* see below */ },
      "operationInputs": [ /* optional, see below */ ]
    }
  ]
}
```

Per-test-case key frequency out of **14 112 total test cases**:

| key | count | notes |
|---|---:|---|
| `documentation` | 14112 | always present |
| `expect` | 14112 | always present |
| `params` | 13689 | **absent in 423 cases** — these are the "Missing region" cases where the whole input is empty; treat a missing `params` as `{}` |
| `operationInputs` | 590 | optional |

`params` value types: string 16 926, boolean 27 773, array-of-string 143
(only `dynamodb`'s `ResourceArnList`). Every `params` key is a declared ruleset
parameter name — **0 unknown keys across the corpus** (these are ruleset
parameter names, not builtIn identifiers).

### `expect`

Exactly one of `endpoint` (12 465) or `error` (1 647); never both, never neither.

- **Failure**: `"expect": {"error": "Invalid Configuration: Missing Region"}` —
  a plain string that must match the ruleset's error message exactly. Most common
  messages: `Invalid Configuration: FIPS and custom endpoint are not supported`
  (455), `Invalid Configuration: Missing Region` (422),
  `Invalid Configuration: Dualstack and custom endpoint are not supported` (394).
- **Success**: `expect.endpoint` with keys `url` (12 465, always),
  `properties` (861), `headers` (39). Absent `properties`/`headers` means
  "empty" — the runner should compare against `{}`.

```jsonc
"expect": {
  "endpoint": {
    "url": "https://account-fips.us-east-1.api.aws",
    "properties": { "authSchemes": [ { "name": "sigv4", "signingRegion": "us-east-1" } ] }
  }
}
```

`expect.endpoint.properties` uses the same three keys as rulesets:
`authSchemes` (827), `backend` (102), `metricValues` (34); authScheme keys
`name` (860), `signingRegion` (806), `signingName` (540),
`signingRegionSet` (51), `disableDoubleEncoding` (367).

`expect.endpoint.headers` example (`s3-control`):
`{"x-amz-account-id": ["123456789012"], "x-amz-outpost-id": ["op-01234567890123456"]}`.

### `operationInputs`

An array (590 cases carry one or more entries; 690 entries total). Entry keys:
`operationName` (690, always), `builtInParams` (690, always),
`operationParams` (609). Example:

```jsonc
"operationInputs": [{
  "builtInParams": { "SDK::Endpoint": "https://example.com", "AWS::Region": "us-east-1",
                     "AWS::UseFIPS": true, "AWS::UseDualStack": true,
                     "AWS::Auth::AccountId": "111111111111",
                     "AWS::Auth::AccountIdEndpointMode": "preferred" },
  "operationName": "ListTables"
}]
```

`builtInParams` is keyed by **builtIn identifier** (not parameter name) and uses
exactly the 13 builtIn strings from §3. `operationParams` is keyed by
*operation member name* (26 distinct across the corpus, e.g. `s3:Bucket`,
`s3:Key`, `dynamodb:TableName`, `s3-control:AccountId`, `dynamodb:RequestItems`)
and exercises `contextParam`/`operationContextParams` binding — a runner that
only evaluates `params` can ignore `operationInputs` entirely and still validate
all 14 112 cases.

Total **14 112**. Per service: min 3, Q1 21, median 26, Q3 42, max 548.

## 7. `smithy.rules#endpointBdd`

**It is a compressed/normalized re-encoding of the same ruleset — a reduced
ordered binary decision diagram. It carries no information the `rules` array
lacks. You can ignore it and interpret `endpointRuleSet.rules`.
Confidence: high.**

Structure (identical keys in all 430 models, `version` always `"1.1"`):

| key | type | notes |
|---|---|---|
| `version` | string | `"1.1"` |
| `parameters` | object | same parameter map as the ruleset |
| `conditions` | array | flat, de-duplicated list of `{fn, argv, assign?}` — the same condition grammar as §2 |
| `results` | array | flat list of terminal rules: `{conditions: [], type: "endpoint"\|"error", ...}` (2499 endpoint / 2495 error results corpus-wide) |
| `root` | int | index of the root node |
| `nodeCount` | int | number of nodes |
| `nodes` | string | base64, **12 bytes per node** = three big-endian int32. Decoding `sts` gives triples like `(-1, 1, -1)`, `(0, 30, 3)`, `(1, 4, 100000014)` — read as (condition index, high branch, low branch), with negatives as terminals and a large bias (~`100000000`) marking result references. Exact bias semantics were not reverse-engineered; not needed if you use `rules`. |

Evidence it is equivalent, not additive:
- `nodes` decodes to exactly `nodeCount × 12` bytes in every model checked.
- `bdd.parameters` is byte-identical to `endpointRuleSet.parameters` in 425/430
  models; the 5 differences are cosmetic only — the BDD normalizes `"String"`→
  `"string"`/`"Boolean"`→`"boolean"` and materializes `required: false` where the
  ruleset omits it (`acm`, `agent-registry`, `agent-registry-control`,
  `pricing-plan-manager`, `signer-data`).
- `bdd.conditions` and `bdd.results` use the same `fn`/`endpoint`/`error` shapes.
- Every BDD-bearing model also has a non-empty `rules` array; **no model has a
  BDD only**. `elastic-transcoder` has rules but no BDD, proving the BDD is optional.
- `nodeCount` per service: min 2, median 13, max 553 — tracks ruleset size.

Practical value: the BDD is a size/eval optimization (AWS SDKs use it to avoid
re-walking the tree). A Rust interpreter should implement the tree walker first;
the BDD could later be a faster path over the *same* condition/result vocabulary.

## 9. Things that would surprise an implementer

1. `endpoint.url` is sometimes an object (`{"ref":"Endpoint"}`, 427 sites), not a string.
2. Parameter `type` is not case-normalized: `"String"` / `"Boolean"` appear in 4 models.
3. `endpointTests.version` is `"1"` in 2 models and `"1.0"` in the other 429.
4. 423 test cases have **no** `params` key at all.
5. Assigned variable names vary in case (`PartitionResult` vs `partitionResult`) —
   scope lookup must be exact-match, not canonicalized.
6. `getAttr` paths include bare array indices (`[0]`) and indexed properties
   (`resourceId[3]`), but templates never contain indices.
7. `signingRegion` differs from the URL's region in 278 test expectations —
   returning only a URL from the interpreter is insufficient.
8. `sigv4a` uses `signingRegionSet` (array) instead of `signingRegion`.
9. `properties` can contain non-auth data: `backend: "S3Express"` and
   `metricValues: ["O"]`.
10. Only `s3-control` sets `headers`, and header values are arrays of templates.
11. `not` is used by only 13 services — but is mandatory nonetheless.
12. Max tree depth 18 and 389 rules, both in `s3`; the median service is a flat
    20-rule, depth-5 ruleset, so `s3`/`s3-control`/`dynamodb`/`kinesis` are the
    real correctness targets (they also own 1264 of the 14 112 test cases).
